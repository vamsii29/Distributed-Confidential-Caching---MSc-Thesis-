# Baseline: Valkey local, 2026-11-10

## Environment
- Machine: M3 Pro MacBook, 18 GB RAM, macOS 27.2
- Valkey: v=9.1.3, default config, plaintext (no TEE)
- Client and server on the same machine (loopback)
- Other load during run: <what else was open>

## Command
valkey-benchmark -t set,get -n 100000 -c 50 -d 64

## Results
| Test | Throughput (rps) | p50 (ms) | p99 (ms) |
|------|------------------|----------|----------|
| SET  |       104822     |  0.263   |   0.983  |
| GET  |       106270     |  0.255   |   0.575  |

## What these mean

**Throughput** is how many requests the server completes per unit of time,
measured in requests per second (rps). SET handled 104,822 rps and GET
106,270 rps.

**Latency percentiles** describe how long individual requests took:

- **p50 (median):** half of requests completed at or under this time.
  SET: 50% completed in ≤ 0.263 ms. GET: 50% completed in ≤ 0.255 ms.
  This is the typical request.
- **p99:** 99% of requests completed at or under this time; the slowest 1%
  took longer. SET: 99% in ≤ 0.983 ms, slowest up to 3.543 ms.
  GET: 99% in ≤ 0.575 ms, slowest up to 2.295 ms. This is the tail.

**The average hides the tail.** SET's average (0.276 ms) is almost the same
as its p50 (0.263 ms), so it describes the typical request but says nothing
about the 1% that took about 4× longer or more. Reporting only the average
would make every request look equally fast.

**SET vs GET:** typical latency is nearly identical, but SET has a fatter
tail: p99 is about 3.7× p50 for SET vs about 2.3× for GET. GET's slow
requests are less slow; its typical request is not faster.

**Why p99 matters for a cache:** one page load often makes many cache calls
and waits for all of them. With 100 calls and a 1% chance each of being
slow, the chance that all are fast is 0.99^100 ≈ 0.37, so ≈ 63% of page
loads hit at least one slow call. The tail therefore decides what users
experience. For this thesis, memory encryption in a confidential VM
(SEV-SNP / TDX) may hurt the tail more than throughput, so p99 is the key
metric to compare.

## Caveats

- **Single run:** results can vary between runs; repeat several times and
  report the spread.
- **Background load:** other applications were running on the laptop and
  may have affected results.
- **Client and server on the same machine:** valkey-benchmark competes
  with valkey-server for the same CPU, so the client partly affects the
  measurement. Thesis-grade runs need a separate client machine (MAAS servers).
- **Persistence enabled (unverified cause of SET tail):** the default
  `save` config was active; 100k writes may have triggered a background
  snapshot (fork) during the run. GETs don't write, which fits their smaller
  tail. To test: rerun with `--save ""`.
- **Plaintext baseline only:** no TEE, default config, loopback networking;
  not comparable to cluster or confidential-VM numbers yet.
